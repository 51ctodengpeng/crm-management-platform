## 二、高危

### H1 · 生产实例使用默认管理员口令，且口令已公开

**位置**
- `config.py:402`：`DEFAULT_ADMIN_PASSWORD = os.environ.get("CRM_ADMIN_PASSWORD", "admin123")`
- `bootstrap.py:356-365`：账号表为空时按上述默认值创建 `admin`
- `docs/gzh/CRM推文.md:9,125`：推文中直接写明"演示账号 `admin` / `admin123`"
- 部署侧：`deploy/crm.env.example` **没有** `CRM_ADMIN_PASSWORD` 条目，`install.sh` 也没生成

**成因**
"开箱即用"的默认值没有在生产分支被强制替换。线上 `crm` 库是从本地 SQLite 迁移过去的，`admin` 的口令原样带过来；推文为了让人"直接点进去看"，又把这对口令公开了。

**影响（已实证）**
我在 `https://crm.powershell.com.cn/` 上做了一次（且仅一次）登录验证：

```
首页状态: 拿到登录表单 = True
POST /login -> 200 最终URL: https://crm.powershell.com.cn/
登录成功(出现退出/仪表盘): True
```

即任何读到文章的人都能拿到**管理员**身份，进而：
- 导出全量客户台账 / 项目台账（含联系人手机、微信、邮箱）；
- 在「备份与恢复」里下载整库 zip（含 `crm.db`/`crm.sql` + 全部合同附件）；
- 清空回收站、恢复任意备份、删除全部数据；
- 修改 SMTP 配置、创建新管理员。

**修复方案**

① 立即改线上口令（最高优先级，5 分钟）：

```bash
# 服务器上执行（/opt/crm 为部署目录）
cd /opt/crm && sudo -u crm .venv/bin/python -c "
from app import app
from extensions import db
from models import User
with app.app_context():
    u = db.session.scalar(db.select(User).where(User.username=='admin'))
    u.set_password('换成 16 位随机串')
    db.session.commit()
    print('ok')"
```

同时把推文里的演示账号改成"申请试用 → 单独发放"，或改为只读演示账号。

② 让默认值不再"自动生效"（`config.py`）：


### H2 · 公网注册默认开放，且无验证码 / 频率限制

**位置**：`config.py:361`（`ALLOW_REGISTER = True`）、`config.py:368`（`SITE_DEFAULTS["allow_register"] = "1"`）、`routes/auth.py:132-211`

**成因**：注册开关默认开，且没有 `CRM_ALLOW_REGISTER` 环境变量可以一键关掉；注册接口既无图形验证码，也无 per-IP 速率限制，只靠 `USERNAME_RE` 与口令强度兜底。

**影响**
- 任何人都能批量提交注册（虽然落 `pending` 不自动激活，但会在「账号管理」里堆出成百上千条待审批记录，管理员没法用）；
- 结合 H1，攻击者可以用公开的管理员口令登录后**直接审批**这些账号，形成稳定后门；
- 邮箱枚举：`该邮箱已被其他账号使用` 与 `该账号或邮箱不可用` 的差异可探测某邮箱是否注册（注册页需要，属可接受权衡）；
- `pending` 账号仍写入 `user` 表，账号名会被占用（可用作"抢注"攻击）。

**修复方案**

```python
# config.py
ALLOW_REGISTER = os.environ.get("CRM_ALLOW_REGISTER", "1") == "1"
```

```python
# routes/auth.py：极简滑动窗口限速（进程内即可，多 worker 可用 Redis 替换）
from collections import defaultdict
import time

_register_hits: dict[str, list[float]] = defaultdict(list)

def _rate_limited(key: str, limit: int = 5, window: int = 3600) -> bool:
    now = time.time()
    hits = [t for t in _register_hits[key] if now - t < window]
    hits.append(now)
    _register_hits[key] = hits
    return len(hits) > limit
```

在 `register()` 的 `if request.method == "POST":` 首行插入：

```python
ip = request.remote_addr or "?"
if _rate_limited(f"reg:{ip}"):
    flash("提交过于频繁，请稍后再试", "danger")
    return render_template("auth/register.html", form=form,
                           email_register=mailer.feature_enabled("email_register"))
```

并在线上 `crm.env` 里加 `CRM_ALLOW_REGISTER=0`（内网系统本就不需要公网注册）。

## 三、中危

### M1 · 开放重定向（反斜杠绕过）

**位置**：`routes/auth.py:122-125`

```python
nxt = request.args.get("next")
if nxt and nxt.startswith("/") and not nxt.startswith("//"):
    return redirect(nxt)
```

**成因**：只挡了 `//host` 这种协议相对 URL，没挡 `/\host`。按 WHATWG URL 规范，浏览器解析 http(s) 这类 special scheme 时会把 `\` 当作 `/`，于是 `Location: /\evil.com` 被解析成 `//evil.com` → 跳到外站。

**影响**：`https://crm.powershell.com.cn/login?next=/\evil.com` 登录成功后跳转到攻击者站点，可做高可信度钓鱼（URL 前半段是真实域名，用户点"登录"后才跳走）。需要受害者点击构造链接 + 完成一次正常登录，故定为中危而非高危。

**实测**：

```
'/project/'      -> 允许跳转: True
'//evil.com'     -> 允许跳转: False
'/\evil.com'     -> 允许跳转: True     ← 绕过
'https://evil.com' -> 允许跳转: False
```

**修复**

```python
from urllib.parse import urlsplit

def _safe_next(nxt: str | None) -> str | None:
    """只允许站内相对路径：拒绝反斜杠、协议、主机名与 // 开头"""
    if not nxt:
        return None
    nxt = nxt.strip()
    if "\\" in nxt or "\r" in nxt or "\n" in nxt:
        return None
    if not nxt.startswith("/") or nxt.startswith("//"):
        return None
    parts = urlsplit(nxt)
    if parts.scheme or parts.netloc:
        return None
    return nxt

# 调用处
nxt = _safe_next(request.args.get("next"))
return redirect(nxt or url_for("index"))
```

### M2 · 金额解析接受 `inf / nan / 1e400`

**位置**：`utils.py:530-537`

```python
def parse_amount(value: str) -> float:
    value = (value or "").strip().replace(",", "").replace("¥", "").replace("￥", "")
    if not value:
        return 0.0
    try:
        return round(float(value), 2)
    except ValueError:
        return 0.0
```

**成因**：`float()` 接受 `inf`、`nan`、`1e400`，没有做有限性检查。

**实测**：

```
'inf'    -> inf     finite=False
'-inf'   -> -inf    finite=False
'nan'    -> nan     finite=False
'1e400'  -> inf     finite=False
'1e308'  -> 1e+308  finite=True     ← 也没上限
```

**影响**
- `inf` / `1e308` 落库后，首页"合计（含税）"变成 `inf`，Excel 导出与对账页数字全废；
- **`nan` 会架空超收校验**：`after > project.receivable` 对 `nan` 恒为 `False`，`_check_reconcile` 直接放行，可写入负数/异常金额而不触发拦截；
- 报表 `round()`、`f"{x:,.2f}"` 输出 `inf`/`nan` 文本，前端排序与筛选异常。

**修复**

```python
import math

AMOUNT_LIMIT = 1e12          # 单笔上限 1 万亿，业务上不可能超过

def parse_amount(value: str) -> float:
    raw = (value or "").strip().replace(",", "").replace("¥", "").replace("￥", "")
    if not raw:
        return 0.0
    try:
        num = float(raw)
    except (TypeError, ValueError):
        return 0.0
    if not math.isfinite(num):          # 挡住 inf / -inf / nan / 1e400
        return 0.0
    num = max(-AMOUNT_LIMIT, min(AMOUNT_LIMIT, num))
    return round(num, 2)
```

同时给 `Project.tax_rate`、`credit_days` 这类整型字段加同样的范围夹取（`normalize_tax_rate` 已有兜底，`credit_days` 建议夹到 `0..3650`）。

### M3 · 对账"先查后写"非原子

**位置**：`routes/finance.py:55-101`（`_check_reconcile` 读 `project.matched_amount` → `_do_reconcile` 写 `payment.status`）

**成因**：典型的 check-then-act。校验与写入之间没有行锁，也没有"已对账金额"的数据库级约束。

**影响**：两个并发的对账请求（或批量对账 + 单人操作同时命中同一项目）都能通过校验，导致项目"已收"超过"应收"而不触发任何提示。当前是小团队自用、并发概率低，但这是**金额口径**问题，一旦发生很难察觉。

**修复（MySQL 走行锁，SQLite 走写事务）**

```python
import dbcompat

def _lock_project(project_id: int) -> None:
    """对账前锁住项目行：MySQL 用 SELECT ... FOR UPDATE，SQLite 用写事务"""
    if dbcompat.is_mysql():
        db.session.execute(
            db.text("SELECT id FROM project WHERE id = :pid FOR UPDATE"),
            {"pid": project_id},
        )
    else:
        db.session.execute(db.text("BEGIN IMMEDIATE"))

def _do_reconcile(payment: Payment, allow_over: bool = False) -> str | None:
    _lock_project(payment.project_id)          # ← 新增：先进锁，再读判断
    db.session.refresh(payment.project)        # 取最新 matched_amount
    reason = _check_reconcile(payment, allow_over=allow_over)
    if reason:
        db.session.rollback()
        return reason
    payment.status = "matched"
    payment.reconciled_at = datetime.now()
    payment.reconciled_by = current_user.display_name or current_user.username
    return None
```

批量对账（`batch_reconcile`）逐条提交时也要在循环体内重复上述加锁刷新，否则同一批次的两笔会各读一次旧值。

### M4 · 无 IP 级登录限速；账号锁定可被用来锁死管理员

**位置**：`routes/auth.py:83-102`

**成因**：只有"按账号"的失败计数（5 次 / 15 分钟），没有按来源 IP 的节流。

**影响**
- 任何人都可以故意用错误口令连打 `admin` 5 次，**把管理员锁在门外 15 分钟**，反复打就能长期阻断；
- 由于只按账号计，攻击者换目标账号即可做撞库（password spraying），不会触发任何 IP 侧限制；
- 失败计数是"读改写"（`register_failure` 后 `commit`），并发请求下会丢更新，锁定阈值可被并发绕过。

**修复**

```python
_login_hits: dict[str, list[float]] = defaultdict(list)

def _login_throttled(ip: str, limit: int = 20, window: int = 300) -> bool:
    now = time.time()
    hits = [t for t in _login_hits[ip] if now - t < window]
    hits.append(now)
    _login_hits[ip] = hits
    return len(hits) > limit
```

在 `login()` 的 POST 分支开头：

```python
if _login_throttled(request.remote_addr or "?"):
    flash("尝试过于频繁，请稍后再试", "danger")
    return render_template("auth/login.html"), 429
```

并把账号锁定改为**原子自增**，避免丢更新：

```python
# models.py
def register_failure(self, limit: int, minutes: int) -> bool:
    self.failed_count = (self.failed_count or 0) + 1
    ...
# routes/auth.py：改为数据库端自增写法
db.session.execute(
    db.update(User).where(User.id == user.id)
    .values(failed_count=db.func.coalesce(User.failed_count, 0) + 1)
)
db.session.commit()
db.session.refresh(user)
```

解除锁定不应只靠时间：建议给管理员一个"仅允许来自内网 / 白名单 IP 的登录不受锁定限制"的开关，避免把自己锁死。

### M5 · `/healthz` 泄露数据库异常原文

**位置**：`app.py:98-109`

```python
except Exception as exc:
    return jsonify({"status": "db-error", "detail": str(exc)[:200]}), 503
```

**成因**：探活口为了"方便排错"，直接把异常字符串回显。

**影响**：MySQL 连接失败时会把 `Access denied for user 'crm'@'localhost' (using password: YES)`、主机名、端口、库名回显给**未认证**访问者，为后续攻击提供精准信息（用户名、认证方式、内网拓扑）。

**修复**

```python
@app.route("/healthz")
def healthz():
    from flask import jsonify
    try:
        db.session.execute(db.text("SELECT 1"))
    except Exception as exc:
        app.logger.exception("健康检查失败")          # 细节只进日志
        return jsonify({"status": "db-error"}), 503   # 对外只给状态
    return jsonify({"status": "ok", "db": app.config.get("DB_BACKEND"),
                    "version": app.config.get("APP_VERSION", "")})
```

### M6 · 恢复备份无体积上限；恢复期间无互斥

**位置**：`routes/backup.py:278-295`

**成因**：`_restore_from_zip` 直接 `zf.extract(...)` 遍历全部成员，既不校验条目数，也不算解压后总体积；`MAX_CONTENT_LENGTH=20MB` 只限制上传压缩包本身大小，对解压比没有约束。

**影响**：一个 20MB 的高压缩比 zip 可解出几十 GB，瞬间打满 `/opt/crm` 所在分区，导致附件写入失败、备份失败、乃至整机不可用。另外恢复过程会替换库文件 / 灌 SQL，但没有与其它 worker 互斥，恢复窗口内的并发写会丢失或写入被覆盖的库。

**修复**

```python
MAX_MEMBERS = 20000
MAX_TOTAL_BYTES = 4 * 1024 ** 3

with zipfile.ZipFile(path) as zf:
    infos = zf.infolist()
    if len(infos) > MAX_MEMBERS:
        return False, f"备份包条目过多（{len(infos)}），已拒绝恢复"
    total = sum(i.file_size for i in infos)
    if total > MAX_TOTAL_BYTES:
        return False, f"备份包解压后体积异常（{total // 1024 // 1024}MB），已拒绝恢复"
    ...
```

互斥用一个文件锁把恢复串行化：

```python
import fcntl
lock_file = Path(Config.DATA_DIR) / ".restore.lock"
with open(lock_file, "w") as fh:
    try:
        fcntl.flock(fh, fcntl.LOCK_EX | fcntl.LOCK_NB)
    except OSError:
        return False, "另一个恢复任务正在进行，请稍后再试"
    ...  # 原有恢复逻辑
```

> 补充：`zipfile.extract` 本身**不会**被 `../` 穿越——见第五节第 5 条实测，该指控不成立。这里的风险只有体积与并发。

## 四、低危

### L1 · `.secret_key` 未收敛权限

`config.py:141` `key_file.write_text(key)` 用默认 umask，Linux 上通常是 `644`，同机其他用户可读；拿到它就能伪造任意会话 / CSRF 令牌。

```python
try:
    key_file.write_text(key, encoding="utf-8")
    os.chmod(key_file, 0o600)      # ← 新增
except OSError:
    pass
```

（`deploy/install.sh` 已对 `crm.env` 做过 `chmod 600`，但 `crm.env` 里的 `CRM_SECRET_KEY` 会优先于文件生效，两者都要收权限。）

### L2 · 账号枚举

`routes/auth.py:98` 的"还可尝试 N 次"只在账号存在时出现；注册页 `该账号「x」已被注册` 同理。
建议：登录失败统一为"账号或密码错误"，锁定提示只在锁定真正生效时才出现；注册提示改为"该账号或邮箱不可用，请更换或直接找回密码"。

### L3 · 邮箱重置密码后仍被锁定

`routes/auth.py:278-294` 只改了 `password_hash`，没有 `reset_failures()`。用户刚重置完密码，仍要等锁定到期才能登录，体验上像"重置无效"。

```python
user.set_password(new)
user.reset_failures()        # ← 新增
row.used_at = datetime.now()
db.session.commit()
```

### L4 · 退出登录是 GET

`routes/auth.py:305-311`。任意页面放一个 `<img src="https://crm.../logout">` 就能把用户踢下线（危害有限，但属 CSRF 类缺陷）。
建议改为 `methods=["POST"]`，模板里用隐藏表单提交；若要保留旧链接兼容，可在 GET 分支里直接渲染一个带 CSRF 的确认按钮。

### L5 · 导入暂存 JSON 无 TTL 清理

`routes/imports.py:284-293` 每次预览都在 `DATA_DIR/tmp` 落一份 `import-<hex>.json`，只有 commit 成功或主动放弃才会删。用户传了文件不提交，文件就长期留存（含客户手机、邮箱等明细）。
建议在 `bootstrap()` 结尾加一次性清扫：

```python
tmp_dir = Path(Config.DATA_DIR) / "tmp"
cutoff = datetime.now().timestamp() - 24 * 3600
for f in tmp_dir.glob("import-*.json"):
    try:
        if f.stat().st_mtime < cutoff:
            f.unlink()
    except OSError:
        pass
```

### L6 · 暂存 token 未与会话绑定

`routes/imports.py:371`：`token = request.form.get("token") or session.get(TOKEN_KEY)`。token 是 `uuid4().hex`，不可猜，所以实际不可利用；但更稳的写法是把它与 `session[TOKEN_KEY]` 比对一次：

```python
token = request.form.get("token") or session.get(TOKEN_KEY)
if token != session.get(TOKEN_KEY):
    flash("导入会话不属于当前登录，请重新上传", "warning")
    return redirect(url_for("imports.index"))
```

### L7 · 流水号唯一索引创建失败被静默吞掉

`dbcompat.py:99-101` 里 `except Exception: rollback(); return "skipped"`。历史数据已有重复流水号时索引建不出来，之后"一笔记两次"就没有数据库兜底了，而调用方只看到 `skipped` 并不会提示任何人。
建议：`current_app.logger.warning` 记下原因，并在「收款对账」页顶部给一条常驻提示（`skipped` 时显示"流水号唯一约束未生效，请人工核对重复流水号"）。

### L8 · `CRM_DEBUG=1` 可开启 Werkzeug 调试器

`app.py:693-697`：`debug = os.environ.get("CRM_DEBUG", "0") == "1"`，随后 `app.run(host="0.0.0.0", debug=debug)`。默认关，但一旦有人在生产 `crm.env` 里为排错加上这一行而忘了删，等于把 Werkzeug 交互式调试器（可执行任意代码）暴露到公网。
建议加硬闸：

```python
debug = os.environ.get("CRM_DEBUG") == "1" and os.environ.get("CRM_ENV") == "dev"
```

（另：`desktop.py` 默认 `127.0.0.1`、需显式 `--host 0.0.0.0` 才对外，且启动横幅已有警告，此项无需改。）

### L9 · 待办提醒邮件的 HTML 注入

`routes/todo.py:50`：`body = "<ul>" + "".join(f"<li>{line}</li>" for line in items) + "</ul>"`，`line` 里含项目名 / 客户名（用户可自填），未经转义就拼进 HTML 邮件。
邮件客户端普遍禁脚本，所以危害限于"排版被搞乱 / 插入钓鱼链接/图片"。修复一行：

```python
import html as _html
body = "<ul>" + "".join(f"<li>{_html.escape(line)}</li>" for line in items) + "</ul>"
```

## 五、对"GPT 说有一堆漏洞"的逐条核实

没有拿到对方的原始清单，我按业内工具最常报的 20 类做了逐条核对。**判定标准：能找到可复现路径才算成立。**

| # | 常见指控 | 结论 | 依据 |
| --- | --- | --- | --- |
| 1 | SQL 注入 | **不成立** | 全量 ORM / 参数化；裸 SQL 仅出现在 `bootstrap.py`（DDL 常量）、`app.py:102`（`SELECT 1`）、`backup.py:204`（常量聚合）、`dbcompat.py`（标识符经 `q()` 加引号），无任何用户输入拼接 |
| 2 | 存储型 XSS | **不成立** | 全项目模板 **0 处** `\|safe` / `Markup` / `autoescape false`；文本预览走 `preview_text.html` 由 Jinja 转义；`send_file` 只对 pdf/图片放行，且全局 `X-Content-Type-Options: nosniff` |
| 3 | CSRF | **不成立**（仅 L4 属同类小缺陷） | 全局 `CSRFProtect`，含登录/注册在内所有 POST 表单带 `csrf_token`；未带 token 的跨站请求一律 400 |
| 4 | 上传可执行文件 / webshell | **不成立** | `allowed_file()` 黑名单 + 白名单双检；物理名 `uuid4().hex.ext`；`uploads/` 不在静态目录、不直出；下载强制 `as_attachment` |
| 5 | Zip Slip（解压穿越写文件） | **不成立（实测）** | CPython `zipfile.extract` 会剥离 `..`：`../../pwned.txt` → 落在 `out/pwned.txt`，`上级目录被写入: False` |
| 6 | 路径穿越读文件 | **不成立** | `backup.download/delete` 校验 `target.parent == backups`；附件走 `resolve_abs_path`（限 `uploads/` 内）；头像走 `Path(name).name`；`profile.avatar_file` 同 |
| 7 | 越权 / IDOR | **不成立** | AST 扫描 93 条路由逐条核对：客户/项目详情·编辑·删除挂 `*_access_required`；附件 `_guard()` 继承项目权限；收款 7 处 `has_project_permission`；导出、全局搜索、待办、操作日志均带 `apply_*_scope`；管理员功能 `@admin_required` |
| 8 | 明文存储口令 | **不成立** | `generate_password_hash` / `check_password_hash`（werkzeug 默认 scrypt）；SMTP 口令可逆加密，见第 9 条 |
| 9 | 自研加密不可靠 | **部分成立（L 级）** | `mailer.py:34-73` 是 SHA256-CTR + HMAC（encrypt-then-MAC），构造本身没破绽，但密钥由 `SECRET_KEY` 派生且与密文同机存放，只防"备份包外泄"。建议换 `cryptography.Fernet` |
| 10 | 硬编码 SECRET_KEY | **不成立** | `config.py:129-145`：环境变量 → `.secret_key` 文件 → 随机生成并落盘 |
| 11 | 会话固定 | **不成立** | 登录成功 `session.clear()` 后再 `login_user`；`HttpOnly` + `SameSite=Lax` + 生产 `Secure`；空闲 120 分钟超时 |
| 12 | 生产开 debug | **部分成立（L8）** | 默认 `CRM_DEBUG=0`，只有显式设为 `1` 才开 |
| 13 | 缺安全响应头 | **不成立** | `after_request` 统一下发 `nosniff` / `SAMEORIGIN` / `Referrer-Policy` / 生产 HSTS / `CSP frame-ancestors 'self'` |
| 14 | 默认管理员口令 | **成立 → 高危 H1** | 线上实测 `admin/admin123` 可登录，且口令已随推文公开 |
| 15 | 无暴力破解防护 | **成立 → 中危 M4** | 有账号级锁定，但无 IP 节流，且锁定可被用于拒绝服务 |
| 16 | 开放重定向 | **成立 → 中危 M1** | `/\evil.com` 绕过前缀检查 |
| 17 | 输入校验缺失（数值） | **成立 → 中危 M2** | `parse_amount` 接受 inf/nan；文本类字段普遍有 `[:32]/[:64]` 截断，无溢出 |
| 18 | 敏感信息泄露（探活口） | **成立 → 中危 M5** | `/healthz` 回显 DB 异常原文 |
| 19 | 资源未释放 / 句柄泄漏 | **不成立** | 文件读写全部 `with`；`sqlite3` 连接 `finally: close()`；`subprocess.run` 带超时路径、无 `shell=True`；`tempfile.TemporaryDirectory` 自动清理；`restore` 的 `tmp_dir` 在 `finally: rmtree` |
| 20 | 日志泄露敏感信息 | **不成立** | `log_action` 只记动作、对象名与操作人；SMTP 口令不落日志、不回显页面（只回 `has_password`） |

## 六、整体修复情况与仍需关注

**本轮性质**：只做审计与取证，**尚未改动任何业务代码**（验证用的临时脚本已删除）。上线实例仍为审计时状态。
