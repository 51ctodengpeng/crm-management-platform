> 实施日期：2026-10-17　｜　环境：本地源码 + 测试服务器 `https://crm.powershell.com.cn`（MySQL 8）
> 版本说明：**访问地址字段已于 2026-10-17 22:45 下线**（详见第三节），当前日志页展示的是「客户端」与「客户省市」。

本次在操作日志上做了三件事，并对客户地区做了一次结构化补齐：

1. 操作日志新增 **客户端类型**（保留）；
2. 操作日志新增 **客户省市**，从客户主档实时关联；

4. 客户新增 **省 / 市 / 区** 三级结构化字段。

## 一、操作日志：客户端类型（`operation_log.client_type`）

### 含义

记录这条操作**是用什么设备、什么客户端发起的**，用于区分「本人在电脑上操作」「手机上处理」「第三方脚本调用」等来源。

### 数据结构

| 项目 | 说明 |
| --- | --- |
| 所在位置 | `operation_log.client_type`（`models.OperationLog`） |
| 类型 | `VARCHAR(64)`，可空 |
| 取值格式 | `大类 · 客户端 版本 · 操作系统`，如 `桌面浏览器 · Chrome 131 · Windows 10/11` |
| 大类枚举 | `桌面浏览器` / `移动浏览器` / `微信内置` / `接口调用` / `未知` |
| 是否必填 | 否。取不到 User-Agent 时落 `未知`；非请求上下文（如启动自检）留空 |

### 数据来源

请求头 `User-Agent`，由 `clientinfo.client_from_agent()` 归一化；`clientinfo.client_type_of()` 负责从请求里取。全部在服务端解析，**不依赖任何前端上报**，也不额外发起请求。

解析顺序（越具体越靠前，避免 Edge / Opera / 微信被误判为 Chrome）：

1. 命令行与脚本工具：`curl`、`Wget`、`Postman`、`python-requests`、`Go-http-client`、`okhttp`、`Java` → `接口调用`
2. `wxwork/` → 企业微信；`MicroMessenger/` → 微信 → `微信内置`
3. UA 含 `Mobile / Android / iPhone / iPad / iPod / HarmonyOS` → `移动浏览器`
4. 其余可识别浏览器 → `桌面浏览器`
5. 空 UA 或无任何特征 → `未知`

操作系统取完整版本后再映射，因此 `Windows NT 10.0` 显示为 `Windows 10/11`、`6.1` 显示为 `Windows 7`，不会把两者混为一谈。

### 局限（重要）

UA 可以任意伪造，因此该字段只用于**区分访问来源类型**，不能当作身份凭据。真实身份始终以登录会话为准。

### 展示

日志页「客户端」列：大类以彩色徽标显示（桌面蓝 / 移动青 / 微信绿 / 接口橙 / 未知灰），下一行小字显示浏览器与系统。悬停表头可见来源说明。

## 二、操作日志：客户省市（新增，不落库）

### 含义

在日志行上直接显示**该操作所涉客户属于哪个省、哪个市**，用于按地域回看「某地的客户最近被谁动过」。日志表本身不新增列，展示时从客户主档关联。

### 为什么不在日志表里存一份

地区属于客户主档，客户改了地址后，历史日志应同步反映。若把省市复制进日志行，就会出现「日志里是旧地址、客户页是新地址」的两套口径，反而更难解释。因此选择**实时关联**，代价是对象被删除后关联不到（见下文缺失规则）。

### 展示格式

| 数据情况 | 展示 | 示例 |
| --- | --- | --- |
| 省、市都有 | 省名 + 市名，**直接相连，不加空格或分隔符** | `广东省深圳市` |
| 只有省 | 只显示省名，不补占位、不猜市级 | `广东省` |
| 只有市 | 只显示市名 | `深圳市` |
| 市名已包含省名 | 只保留较长的那个，避免重复 | `北京市` + `北京市` → `北京市`；`上海` + `上海市` → `上海市` |
| 都未填写 / 关联不到客户 / 该类型不涉及客户 | 统一显示 `—`（灰色），悬停提示「无客户归属地：对象已删除、不涉及客户，或客户未填写省 / 市」 | `—` |

> 与客户列表不同：列表里的「所在地区」仍用空格拼接（`江苏省 苏州市 吴中区`），那是既有口径，未改动。日志里采用紧凑写法，与需求给的示例（`广东省深圳市`）保持一致。

### 数据来源与关联路径

`operation_log` 只存 `target_type` + `target_id`，展示时按类型反查客户：

| 对象类型 | 关联路径 |
| --- | --- |
| 客户 | `target_id` 即客户 id |
| 项目 | `project.customer_id` |
| 附件 | `attachment.project_id → project.customer_id` |
| 收款 | `payment.project_id → project.customer_id` |
| 账号 / 系统 / 选项 / 系统设置等 | 不涉及客户 → `—` |

实现集中在 `logregion.py`：

- `format_region(province, city)`：纯函数，负责上面的拼接与去重规则；
- `resolve_log_regions(logs)`：对**当前这一页**的日志一次性批量关联，整页至多 5 条查询（客户、项目、附件、收款、客户地区各一条），不做逐行查询、不写回日志表。

### 缺失与边界

1. **对象已删除**（如「删除客户」这类日志）：源记录已不存在，反查不到 → `—`。回收站里仍有快照，恢复后新产生的日志才会带地区；**不按文本推断、不回填**。
2. **历史客户只有 `region` 文本、没有省 / 市列**（三列是 2026-10-17 才补的）：同样显示 `—`。编辑该客户并保存后三列被补齐，**之后**的日志才会有值。
3. **普通成员只能在日志页看到自己的操作**（既有规则），地区信息不扩大可见范围。
4. 关联查询失败时只记一条告警日志、该列整体回落 `—`，不会让日志页 500。

## 三、访问地址（已下线）

### 变更内容

2026-10-17 22:45 起，操作日志的「访问地址」属性按要求移除：

| 层面 | 处理 |
| --- | --- |
| 页面展示 | 「访问地址」列已删除，日志页现为 8 列（时间 / 操作人 / 动作 / 对象 / 详情 / 客户省市 / 客户端 / IP） |
| 写入 | `utils.log_action()` 不再读取请求路径与查询串，也不再写 `access_url` |
| 代码 | `models.OperationLog.access_url` 字段定义、`bootstrap.NEW_COLUMNS` 的补列项、`clientinfo` 的 `scrub_url / request_url / client_info` 与敏感参数表全部删除 |
| 数据库列 | **保留不动**。已有列与历史数据不删除、不迁移、不回填（`VARCHAR(300)` 可空，模型不再映射后新记录写入为 `NULL`） |

数据库列选择保留而非 `DROP COLUMN`，原因是删列不可逆、且旧数据仍有取证价值；如确认不再需要，可在业务低峰期手动执行：

```sql
ALTER TABLE operation_log DROP COLUMN access_url;
```

### 影响

日志页少一列，其余功能（登录、对账、导入、导出、回收站）不受影响；`client_type` 的写入与展示照旧。

## 五、客户省市区（`customer.province / city / district`）

### 为什么不是「新加一个字段」而是「把已有选择结构化」

系统**早已有**省/市/区三级联动选择器（`static/js/region-picker.js` + `static/data/regions.json`），表单提交的也是 `province`、`city`、`district` 三个参数。但后端此前只把它们拼成一段文本写进 `customer.region`，拆分信息随即丢弃。

因此本次不是再造一个地区控件，而是把这三段**按原样落库**，让数据可以被统计和筛选——日志里的「客户省市」正是它的第一个消费方。

### 数据结构与层级

| 层级 | 字段 | 类型 | 示例 | 必填 |
| --- | --- | --- | --- | --- |
| 省 / 直辖市 / 自治区 | `customer.province` | `VARCHAR(32)`，可空，建索引 | 江苏省 | 否 |
| 市 | `customer.city` | `VARCHAR(32)`，可空 | 苏州市 | 否 |
| 区 / 县 | `customer.district` | `VARCHAR(32)`，可空 | 吴中区 | 否 |

层级关系由 `regions.json` 维护：`省 → 市 → 区` 逐级联动，市级选项只会是当前省的下级，区级同理。直辖市（如北京市）在数据里省与市同名，三级依然完整。

### 必填性与一致性约束

- **整体非必填**，与原有「所在地区」一致：公司名称才是唯一必填项，地区可以留空。
- 但落库时强制**层级自洽**：省为空 → 市、区一并置空；市为空 → 区置空。避免「省空、区有值」这类无法按省统计的脏数据。

### 与 `region` 的关系（兼容性的关键）

`customer.region` **保持原样，仍是唯一的展示口径**——客户列表、全局搜索、导出、查重、导入全部继续读它，一个字都没改。

- 选了三级：`region = "江苏省 苏州市 吴中区"`（原有拼接逻辑不变），同时写入三列；
- 手动填写：`region = 用户输入原文`，三列留空（不猜测、不硬拆）；
- 历史数据：`region` 有值、三列为 `NULL`，页面照常显示 `region`；编辑时 `region-picker.js` 会从文本里解析并回填下拉，保存后自然补齐三列——**渐进式迁移，不需要批量刷数据**。

详情页「所在地区」主行仍显示 `region`，仅当三列有值时在下方追加省/市/区三枚徽标（悬停标注层级），不改变主文案。

### 一处顺带修正

`migrate.py` 结尾的统计原先手写 `SELECT COUNT(*) FROM "user"`，SQLite 认双引号、MySQL 只认反引号，在服务器上执行会抛 1064。现改用 ORM 计数，两种后端通用。

## 八、已知边界

1. **UA 可伪造**，`client_type` 只能作为来源分类参考，不能作为安全证据；真正的身份依据仍是 `username` + 会话。
2. **IPv6 与反向代理**：`ip` 列沿用原有逻辑，`BEHIND_PROXY=1` 时由 ProxyFix 还原真实来源地址；本次未改动。
3. **客户省市是实时关联而非快照**：客户改地址后，历史日志会随之变化；客户或项目被删除后，相关日志显示 `—`。这是「不落冗余」的必然结果，已在上文写明。
4. **旧日志不会被回填**。历史记录的 `client_type` 保持 `NULL`，页面显示 `—`；不做推测性补全，避免制造伪历史。
5. **`access_url` 列仍在数据库中**，只是不再读写。确认不需要后可按第三节的 SQL 手动删除。
